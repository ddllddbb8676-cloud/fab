## 1. 가장 먼저 알아야 할 상태

- **조이스틱·이동 속도·술래잡기용 넓은 시야 변경은 구현, 테스트, 운영 배포, Git push까지 완료했다. 사용자는 현재 조작감을 좋아한다고 했다.**

- 선택형 카카오·구글 로그인은 별도 보류 작업이다. 꾸미기를 진행한다고 로그인까지 시작하지 않는다.

## 3. 이어가던 대화: 칩과 꾸미기

### 사용자가 직접 정한 내용

사용자는 화면을 복잡하게 만들지 않는 재미 요소를 원했고, 기록에 따라 캐릭터 장식품을 사는 방식을 제안했다. 이어서 다음 보상안을 직접 제시했다.

| 성공한 행동 | 칩 |
| --- | ---: |
| 장비 한 대 파괴 | 5 |
| 장비 한 대 수리 완료 | 3 |
| FOUP 한 번 던지기 | 1 |
| 캐릭터가 OHT에 실제 탑승한 상태로 10초 경과 | 1 |

사용자 의도: **파괴가 수리보다 칩을 많이 준다.** 임의로 두 보상을 뒤집지 않는다.

OHT 시간에 대한 가장 마지막 수정은 **“아냐 내리면 끝이야”**였다. 여러 번 탑승한 잔여 시간을 합산하자는 제안을 사용자가 거절한 것이다.

- 한 번의 탑승 안에서만 10초마다 1칩을 받는다.
- 내리면 이번 탑승에서 10초를 채우지 못한 잔여 시간은 버리고 타이머를 0으로 돌린다.
- 다시 타면 새로 0초부터 센다. 이미 받은 칩을 회수한다는 뜻은 아니다.
- 예: 7초 탑승 후 하차 → 0칩. 다시 3초 탔다고 1칩이 되지 않는다.
- 예: 17초 탑승 후 하차 → 1칩, 남은 7초는 폐기.
- 예: 20초 탑승 후 하차 → 2칩.
- 실제 탑승과 단순 OHT 관람 카메라는 구분해야 한다. 구현 시 서버의 실제 승객 상태를 지급 기준으로 삼는 것이 적합하다.

### 제안만 했으며 확정되지 않은 내용

다음은 이전 답변의 제안 또는 후속 구현 권장안이다. **사용자가 모두 승인한 결정처럼 다루지 않는다.**

- 파괴·수리 누적 기록과 소비 가능한 칩 잔액을 분리한다. 물건을 사도 랭킹 점수는 줄이지 않는 방향.
- 기존 이용자의 과거 기록으로 최초 칩을 지급하는 안: `파괴 횟수 × 5 + 수리 횟수 × 3`. **소급 지급 여부 자체가 미정**이다. 지급한다면 한 번만 처리해야 한다.
- 지갑·보유 장식품·장착 상태를 기존 프로필에 저장해 새로고침 후 유지하는 방향.
- 상점 진입은 `메뉴 → 꾸미기`처럼 배치하고, 기본 게임 화면에는 큰 상점 패널이나 상시 칩 표시를 추가하지 않는 방향.
- 아이템 예: 새싹·작은 왕관·웨이퍼 머리 장식, 작은 FOUP 가방, 민트·하늘색·보라색 계열의 방진복 포인트.
- 안전팀을 구분할 수 있도록 빨강·주황 계열은 안전팀 식별용으로 남기는 방향.
- 장식품은 외형만 바꾸고 속도·포획·수리 능력은 바꾸지 않는 방향.

아직 정하지 않은 것: 최초 아이템 목록, 가격, 장착 슬롯, 기존 기록 소급 지급, 안전팀 활동 보상, 안전팀 상태에서의 일반 칩 지급 범위, 구매 확인 UI. 실제 돈 결제, 유료 아이템, 일일 보상 제한, 임의의 적립 상한은 요청받지 않았다.

이전에 나온 대시·FOUP 변장·협동 수리·황금 FOUP 등은 아이디어였을 뿐, 현재 추가해야 할 기능 목록이 아니다.

### 새 대화에서 권장하는 첫 진행

1. 현재 코드와 이 문서를 확인하고, 조이스틱은 완료·꾸미기는 기획 단계라는 상태를 유지한다.
2. 작은 1차 아이템 목록·가격 및 소급 지급 권장안을 짧게 정리한다. 사용자가 이미 정한 보상 수치와 OHT 하차 규칙을 재질문하지 않는다.
3. 구현 요청이 이어지면 기존 프로필을 확장하고 서버에서 보상·구매를 처리한다. 아래 저장·호환성 주의사항을 지킨다.

## 4. 현재 게임 기능과 반드시 유지할 조건

### 공간과 상호작용

- FAB은 120m × 180m, 층고 5m. 18개 BAY, 관람 장비 360대. 규모를 줄이지 말라는 사용자 요구가 있다.
- 각 BAY는 장비 10대씩 두 줄이 마주 보는 구성이다. 전면 통로 5.2m, 뒤쪽 서비스 통로 1.4m, 같은 줄 장비 사이 틈 0.65m.
- 로드포트 바로 위 OHT 선로와 여러 분기·교차로가 연결된다. 장비·로드포트·OHT 좌표의 일관성을 유지한다.
- 포토·메탈·금속 전용 세정 BAY의 노란 조명, 에어샤워 입장과 자동문 닫힘을 구현했다.
- 장비 이름은 `PHA0101` 같은 7자리: 공정 2자 + FAB 1자 + BAY 2자 + 장비 순번 2자. PH·ET·CL·CM·CV·ME·DI·IM, 계측 MT·검사 IN·소터 SO를 사용한다.
- 월 3만 장 DRAM 투입에 대한 공개 자료 기반 용량 계산 문서가 있으나, 실제 레시피나 실제 팹 설계 검증 결과는 아니다. 공간과 관람 장비 수는 유지했다.
- EMO는 빨간 버튼 부근을 선택해야 한다. 캐릭터가 가까이 가서 손으로 누른 뒤 장비가 폭발·붕괴하며 효과음이 난다.
- 파손 장비는 한 대씩 걸어가 수리한다. 수리 찾기는 가까운 순서이며 모바일 키보드를 띄우는 검색창을 없앴다.
- 시야를 가려 투명해진 장비가 바닥 클릭을 가로채는 문제와 파손 장비의 수리 선택 문제를 수정했다. 이후 변경에서도 회귀를 확인한다.
- FOUP 들기·다른 로드포트에 놓기·바닥에 놓기·던지기, OHT 탑승·내리기, 앉기·눕기, 머리 위 감정 표현 6개가 있다.
- OHT 탑승은 앞의 온전한 장비를 밟고 점프해 양손으로 매달리는 행동이다. 기존 화물은 바닥으로 떨어지고, 탑승한 차량은 FAB을 순회한다.
- 효과음·공조음은 상단의 작은 별도 버튼으로 켜고 끈다. 행동 효과음이 날 때 공조음을 낮춘다.

### 인원과 안전팀

**정원 100 = 상주 캐릭터 34 + 실제 방문자 최대 66명.** 예전 30명·36명·실제 방문자 100명 설명으로 되돌리지 않는다. 기준 파일은 `src/room-population.js`다.

| 상주 캐릭터 역할 | 인원 |
| --- | ---: |
| FOUP 놀이 | 5 |
| OHT 탑승 | 5 |
| 휴식 | 5 |
| 수리 | 2 |
| 파괴 | 13 |
| 빨강 안전팀 | 2 |
| 호박 주황 안전팀 | 2 |
| 합계 | 34 |

수리 NPC를 줄인 뒤 없앤 3명은 파괴 역할로 전환했다. 단순히 총원을 줄이지 않는다.

- 유저 안전팀은 처음 입장하자마자 배정하지 않는다. 일정 시간 플레이한 사람을 순번에 따라 한 명씩 배정한다.
- 당시 배정 설정은 준비 60초, 인계 15초, 재배정 대기 90초였다. **11/3 후속 조정:** 첫 배정 누적 5분, 같은 계정의 재배정 대기 10분으로 늘렸다. [최신 기준/검증](safety-duty-frequency-2026-11-03.md)을 따른다.
- **서로 다른 대상 3명**을 잡으면 일반 상태로 돌아온다. NPC도 포함한다. 예전 5명 조건은 폐기됐다.
- 안전팀은 EMO로 장비를 부술 수 없다. 유저 안전팀이 잡으면 성공 안내를 보여준다.
- 잡힌 일반 사용자는 장비 3대를 수리해야 다른 놀이 기능을 다시 사용할 수 있다.
- 잡힌 NPC에는 사용자에게 보이는 것과 같은 수리 안내를 사용하고, 수리하러 가는 듯한 이동을 한다. 별도의 통로 한 바퀴 안내를 띄우지 않는 것이 기존 사용자 요구다.
- 곳곳의 작은 초록 보호 구역과 멀리 보이는 녹색 조명, 안전팀 접근 시 붉은 화면 맥동·경고 문구가 있다.
- 안전팀 이름은 형용사 + `안전팀`. 일반 닉네임은 형용사 + 반도체 용어이며 공백 포함 최대 7자를 목표로 중복을 방지한다. 조합 부족 시 숫자를 붙인다.

### 기록과 화면

- 개인 파괴·수리 횟수와 누적 TOP5가 있다. TOP5는 현재 접속자만이 아니라 저장된 과거 방문자도 포함한다.
- NPC도 기존에 정한 8~11개 수준의 파괴 기록으로 랭킹에 참여하며 0점 항목은 보이지 않게 했다.
- F5·재접속·배포 후에도 같은 브라우저의 사용자 ID·닉네임·카운터·진행 정보를 유지한다.
- `완전히 새로 시작하기`는 사용자가 명시적으로 기록을 초기화하는 예외다. 일반 새로고침과 같은 동작으로 만들지 않는다.
- 파손 장비 상태도 저장한다. 재시작·배포 때문에 장비가 한꺼번에 전부 복구되는 문제를 다시 만들지 않는다.
- 작은 투명 랭킹과 작은 메뉴를 선호한다. 화면을 가리는 큰 버튼·패널을 추가하지 않는다.
- 캐릭터는 짧고 둥근 몸통, 보이는 다리, 자연스럽게 내려오는 팔의 귀여운 방진복 형태를 유지한다. 예전 길쭉한 몸통·짧고 구부린 팔로 되돌리지 않는다.

## 5. 완료된 조이스틱 변경

자세한 기록은 [조이스틱 배포 기록](joystick-release-2026-11-02.md)에 있다.

- 라이브러리: **nipplejs 1.0.4**, 정확한 버전 고정. 설치된 모듈을 빌드에 포함해 CDN에 의존하지 않는다.
- 왼쪽 아래 144px 영역에서 동적 조이스틱을 시작하며 조작 원은 96px이다. 기본 이동은 조이스틱, 화면 드래그는 시점 변경.
- 메뉴에서 기존 바닥 터치 이동으로 전환할 수 있다. `fab-movement-style` 설정을 해당 브라우저에 보관한다.
- 조이스틱 방식에서도 장비 EMO·FOUP·OHT·파손 장비 선택은 가능하다.
- 손을 떼기·취소·창 전환·메뉴 열기로 이동을 멈춘다. 시점 조작 손가락을 떼는 것이 이동 손가락까지 종료시키지 않게 분리했다.
- 대각선 입력이나 원 밖 드래그로 추가 가속하지 않으며 카메라 기준으로 이동한다.

| 값 | 현재 |
| --- | ---: |
| 플레이어 이동 | 3.2m/s |
| NPC 일반 / 수리 / 안전팀 | 1.7 / 2.0 / 2.1m/s |
| 기본 카메라 거리 | 5.8m |
| 기본 카메라 고도각 | 0.56rad |
| 기본 수직 화각 | 72도 |

기준 파일: `src/locomotion.js`, `src/touch-joystick.js`, `src/explorer.js`, `src/walking.js`. 직접 조작의 가속·방향 전환을 높였고, 이동 방향에 맞춰 카메라가 강제로 돌아가지 않도록 했다. 장비·문·보호 구역 경계 충돌과 카메라 장애물 회피는 유지한다.

nipplejs 1.0.4 이벤트 값은 단일 이벤트의 `event.data.vector`에서 읽는다. 다른 버전의 2개 인자 예제를 그대로 복사하지 않는다. npm 배포본에 라이선스 파일이 빠져 있어 공식 태그의 MIT 고지를 `docs/licenses/nipplejs.txt`로 보관하고 빌드에 복사한다.

### 사용자 식별과 데이터 보존

- 현재 로그인 없이 브라우저의 **HttpOnly 세션 쿠키 `fab-session-v1`**로 같은 사용자를 식별한다. 무작위 토큰을 해시해 내부 `visitor:` ID와 연결한다.
- 쿠키는 HTTPS에서 Secure, SameSite=Lax, 최대 1년으로 발급된다. 여기에는 실제 토큰 값을 기록하지 않는다.
- 서버 프로필 키는 `profile:<사용자 ID>`, 장비 파손 상태 키는 **`world:equipment:v1`**이다.
- 동일 브라우저·동일 사이트 쿠키가 유지되면 기존 프로필로 복귀한다. 쿠키 삭제·시크릿 창·다른 브라우저·다른 기기는 현재 자동 연결되지 않는다.
- 주요 프로필 필드: ID·일반/안전팀 이름·역할·`brokenCount`·`repairedCount`·패널티·플레이 시간·안전팀 차례/포획 진행·입장 여부·지상 위치.
- `server/room-engine.js`의 `profile(p)`, `join(id, saved)`, `changed(p)`와 `server/player-profiles.js` 저장 경로를 함께 확인한다. 새 필드를 한쪽에만 추가하면 재접속 때 사라질 수 있다.
- 현재 저장기는 쓰기를 직렬화하고 실패한 쓰기를 재시도 대상으로 보존한다. 쿠키 초기화나 프로필 덮어쓰기 없이 필드를 확장해야 한다.
- `/api/leaderboard`는 누적 랭킹이다. 온라인 플레이어 목록만으로 바꾸지 않는다.
- `/api/session/reset`은 명시적인 새로 시작 동작이다. 일반 새로고침에서 호출하지 않는다.

**`FAB-A-v20` 방 이름을 바꾸면 새 Durable Object 방을 선택할 수 있다.** 캐시 갱신 용도로 방 이름·저장 키·마이그레이션을 임의 변경하면 사용자의 기록이나 파손 상태가 사라진 것처럼 보일 수 있으므로 기존 방을 유지하며 호환성을 설계한다.

### 칩을 구현할 때 확인할 정확한 지점

아래는 구현 지침이며 **현재 구현된 칩 기능 설명이 아니다.** 현재 소스에는 칩 잔액·인벤토리·상점이 없다.

1. **파괴:** `room-engine.js`의 `explode`가 서버 검증을 통과하고 `destruction.trigger()`가 성공했을 때 현재 `brokenCount`를 올린다. 이 성공 경로에 5칩 지급을 연결한다. 버튼 클릭·접근 시작·클라이언트 연출만으로 지급하지 않는다.
2. **수리:** 같은 파일의 `finish`가 수리 시간과 대상 상태를 확인하고 `destruction.reset()`에 성공한 뒤 `repairedCount`를 올린다. 이 완료 경로에 3칩을 연결한다. 중단·실패·이미 다른 사람이 수리한 장비는 지급하지 않는다.
3. **FOUP:** 서버의 `throw` 명령은 `data.drop=true`이면 바닥에 놓기에도 쓰인다. **실제 던지기 성공과 단순 내려놓기를 구분**해야 한다. 놓기까지 무조건 1칩으로 계산하지 않는다.
4. **OHT:** `board`는 접근 예약, `climb`은 점프, `ride` 성공 뒤의 `phase='riding'`이 실제 탑승이다. 서버 시간으로 10초 구간을 계산한다. 관람 모드·접근·점프 시간에는 지급하지 않는 기준이 적합하다.
5. **하차:** `dismount`와 공통 `release(p)` 경로를 확인한다. 실제 탑승 종료·취소·접속 종료 뒤 잔여 시간을 다음 탑승에 이월하지 않는다. 새 탑승은 0부터 시작한다.
6. **보존:** 지급·구매 시 잔액과 필요한 원장/마커를 기존 프로필 저장 경로에 연결한다. 클라이언트 localStorage만을 잔액 원본으로 삼지 않는다.
7. **중복:** 재전송된 명령·늦게 도착한 응답·새로고침·중복 구매로 중복 지급하거나 두 번 차감하지 않도록 서버에서 처리한다. 현재 코드에 구매 명령의 멱등성이 이미 있다고 가정하지 않는다.
8. **소급 지급:** 사용자가 승인할 때만 한다. 지급 버전/마커와 잔액을 함께 저장해 F5·재접속·재배포마다 반복 지급되지 않게 한다.
9. **공유 외형:** 자신만이 아니라 다른 접속자에게도 장착품이 보여야 한다. 프로필·장착 알림·원격 캐릭터 표현을 함께 설계한다. 전체 인벤토리를 모든 5Hz 위치 패킷에 싣는 방식은 피한다.
10. **가벼운 렌더링:** 공용 재질을 직접 바꿔 다른 사람 옷색까지 변하지 않게 한다. 장식품은 서기·걷기·앉기·눕기·EMO·수리·FOUP 들기·OHT 매달리기에서 위치를 확인한다. 기존 인스턴싱·거리별 모션 최적화를 보존한다.

서버의 클라이언트 위치 검증은 완전한 부정행위 방지 시스템이 아니다. 새 경제 기능을 만든다고 기존 모든 이동·행동이 강력하게 검증돼 있다고 가정하지 말고, 성공한 서버 행동을 보상 기준으로 사용한다.

node node_modules/wrangler/bin/wrangler.js deploy --dry-run

- 앱 등록·도메인/리디렉션·필요 안내 페이지는 작업 재개 시 준비한다. 이미 구현된 로그인 기능으로 설명하지 않는다.
- 사용자 요청은 “저장만 해둬 나중에 할게”였다. 이번 인수인계나 꾸미기 논의가 로그인 작업 재개를 뜻하지 않는다.

Cloudflare Workers Paid는 사용자가 구매했다. 기본 요금과 별도로 사용량 추가금이 생길 수 있다. 비용 문의가 오면 당시의 계정 사용량과 공식 요금을 다시 확인한다. 예전 계산을 현재 청구액이나 비용 상한으로 제시하지 않는다. 현재 `wrangler.jsonc`의 observability는 꺼져 있으므로 과거 모든 요청의 상세 로그가 남아 있다고 가정하지 않는다.

예약 작업·heartbeat·자동화는 사용자가 명시적으로 요청하지 않는 한 만들거나 활성화하지 않는다. 별도의 팀장·직원 계층을 구성하지 않고 사용자와 직접 협업한다. 현재 환경의 AGENTS 지침을 먼저 확인한다.

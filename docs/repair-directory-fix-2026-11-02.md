# 수리 목록 멈춤·전체 보기 수정 (2026-11-02)

## 증상과 원인

- 모바일에서 안전팀 패널티의 `수리할 장비 찾기`를 누르면 팝업이 나오기 전에 화면이 멈췄다. 기존 구현은 고장 난 장비 전부의 실제 이동 경로를 메인 스레드에서 동기 계산한 후 팝업을 열었다. 사용자 화면의 대상은 255대, 최대 대상은 360대다.
- 팝업 표시 전에 이동을 잠가서, `showModal()`이 실패하는 경우에도 이동 잠금이 남을 수 있었다.
- 패널티 중 `전체 보기`가 메뉴와 시점 전환 함수 양쪽에서 차단돼 있었다.

## 수정

- 수리 목록을 먼저 표시하고 모듈 Web Worker에서 경로를 계산한다. 계산 중 진행 개수와 닫기 버튼이 보이며, 닫으면 작업 종료와 이동 잠금 해제를 함께 처리한다. Worker를 지원하지 않는 환경에서는 장비 한 대마다 이벤트 루프에 제어를 돌려주는 대체 경로를 사용한다.
- `showModal()` 성공 후 이동을 잠근다. 실패 시 잠금을 복구하고 안내한다. 닫은 뒤 재개된 예전 계산 결과는 새 팝업을 덮어쓰지 않는다.
- 고정 장비를 8m 공간 셀에 인덱싱해 충돌 검사마다 360대를 전부 훑는 비용을 줄였다. 실제 장비·로드포트·모니터 지지대의 충돌식과 경계 비교는 그대로다.
- 한 번의 목록 계산 안에서 출발점 연결, 반복 구간의 통과 가능 여부, 통로 간선 검사를 재사용한다. 장애물이 변경되면 캐시를 무효화한다. A* 선택, 접근 자세, 코너 완화와 경로 거리 결과는 동일하다.
- 패널티 중에도 `전체 보기`와 직접 걷기 전환이 가능하다. 3대 수리 조건과 다른 놀이 제한은 유지한다.

## 성능 측정

동일 개발 PC의 Node에서 출발점 `(0, 0)`, 전체 360대, 각 단계 첫 실행으로 비교했다. 실제 휴대폰 브라우저 측정은 아니다.

| 구현 | 360대 경로 계산 |
| --- | ---: |
| 기존 동기 계산 | 7,616ms |
| 장비 공간 인덱스 적용 | 1,477ms |
| 인덱스 + 조회 단위 경로 캐시 | 795ms |

약 9.6배 개선. 기존 360개 거리 값과 정렬 결과가 모두 일치했다. Worker 사용으로 계산 중 화면 메인 스레드도 차단하지 않는다. 팝업 생성은 360행 DOM 모의 환경에서 약 34ms였으며 실제 렌더링 시간과 구분한다.

## 검증

- `npm.cmd run check`, 새 모듈 구문 검사, `npm.cmd run build`, 배포 dry-run 통과.
- `npm.cmd test`: **276개 통과, 실패 0개**.
- 360대 전체의 캐시 경로와 기존 경로 일치, 좁은 통로 및 문 열림/닫힘 후 캐시 무효화 확인.
- 모든 장비 경계와 셀 경계에서 6가지 여유 폭 비교, 20,000개 재현 가능한 무작위 지점에서 기존 전체 충돌 검사와 일치 확인.
- 실제 Worker 모듈을 Node worker_threads 어댑터로 실행해 360대 계산 중 UI 타이머 진행, 장애물 반영, 취소와 늦은 응답 무시 검증.
- DOM 모의 검증: 목록 우선 표시, 닫기/재열기, 수리 선택, 팝업 실패 시 이동 잠금 복구, 패널티 중 전체 보기 버튼 활성화.
- 기존 조이스틱·EMO·문·수리·칩·사용자 저장 회귀 검사 포함.
- 실제 iPhone/Instagram 내장 브라우저 조작 검증은 수행하지 않았다. 현재 환경에서 브라우저 제어가 비활성화돼 있다.
